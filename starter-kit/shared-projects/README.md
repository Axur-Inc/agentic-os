# Shared Projects

Work in flight. Whitepapers being co-authored, decks being prepared, plans under construction, anything where multiple people are contributing in real time.

## Conventions

- One subdirectory per active project.
- Each project has its own `README.md` describing the work, the contributors, the status, and the deliverables.
- Use status markers (`[TBD]`, `[DRAFT]`, `[NEEDS-UPDATE]`) inside files to signal what is settled and what is in flight.
- Branch-per-default for non-trivial changes. Trivial single-file edits (typo fixes, date updates) can go directly to main.

## What goes here vs. knowledge-base/

`shared-projects/` is for work in flight. `knowledge-base/` is for stable reference. When a project finishes and its output is useful as long-term reference, promote the final artifact to `knowledge-base/` and either archive the working folder or delete it.

## Lifecycle

A typical project moves through:

1. **Started.** Subdirectory created, README outlines scope.
2. **In flight.** Drafts, contributions, reviews. Most activity happens here.
3. **Settled.** Final artifact emerges. Decision: archive or promote.
4. **Promoted.** Artifact moves to `knowledge-base/` under the appropriate domain.
